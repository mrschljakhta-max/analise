# ANALISE · Збережені документи та відкладена перевірка RAW

## Призначення

Після збереження DOCX/XLSX у Cloudflare D1 через `/api/generic-preview` оператор відкриває `/api/saved-documents` і працює з уже підтвердженою RAW-версією.

- Версії читаються з `report_versions` (namespace `ANALISE-RAW-V1:`), по 30 записів з пагінацією.
- Кожен документ можна відкрити за його незмінним ID, перемикати аркуші Word/Excel, переглядати значення та статуси структурної перевірки по 20 рядків.
- «Чистилище» запускається **пізніше**: користувач сам обирає версію, конкретну колонку й довідник. Ніяких автоматичних припущень про семантику чи типи джерел.
- Передача до `dq_occurrences` виконується лише після явного підтвердження, порціями по 60 вихідних рядків. Сервер читає значення з D1, а не приймає довільні значення з браузера.
- Порожні/надто довгі/некоректні значення не передаються; оператор бачить підсумок пропусків, їх не позначають опрацьованими.
- Вхідний `source_id` має формат `raw:<version_uuid>`, а `source_ref` включає ID версії, індекс таблиці, номер рядка та поле. Повторне передавання того самого набору використовує `ON CONFLICT` існуючого `ingest`: зберігаються рішення, підтверджені вручну для незмінного значення.
- Статус із `/api/raw-review/:id/quality` рахується тільки для **переданих до Чистилища** входжень. Це не статус завершеної перевірки всіх записів і **не** автоматична публікація якості всього документа.
- Записи RAW **не оновлюються** при перевірці: рішення та аудит окремо в `dq_occurrences`, `dq_rules`, `dq_audit`.

## Маршрути

- `GET /api/saved-documents`, `GET /api/saved-documents.css`, `GET /api/saved-documents.js` — приватна сторінка, доступ `admin`.
- `GET /api/raw-documents?offset=N` — перелік по 30 версій; `has_more`.
- `GET /api/raw-documents/:uuid` — існуюче читання первинної JSON-версії.
- `GET /api/raw-review/directories` — довідники для вибору адміністратором.
- `GET /api/raw-review/:uuid/quality` — статуси черги для конкретної версії.
- `POST /api/raw-review/:uuid/queue` — передавання наступних 60 рядків вибраної колонки в існуючий `/api/purgatory/ingest`.

`POST` приймає **лише** `{directory_id, table_index, column, offset}`. Самі значення на сервері читаються з D1, перевіряються на форму й передаються в наявне «Чистилище» з журналом аудиту. Не відбувається авто-зіставлення полів із військовими/іншими специфічними довідниками.

## Приймальний сценарій

1. Відкрити `/api/saved-documents` через Cloudflare Access як адміністратор.
2. Перевірити перелік раніше збережених RAW, зокрема DOCX і XLSX, та переходи між сторінками.
3. Відкрити RAW-версію, звірити кількість записів і її незмінні значення.
4. Вибрати аркуш/таблицю, вручну вибрати колонку і відповідний довідник.
5. Підтвердити передавання до «Чистилища». Для тесту використати дозволені синтетичні значення, без координат, частот, маршрутів чи інших оперативних даних.
6. Натиснути «Відкрити Чистилище», переглянути чергу та підтвердити тестове входження. Повернутися до RAW і перевірити окремі лічильники pending/resolved/ignored.
7. Повторити передавання того самого поля: дублікати входжень не створюються, незмінні ручні рішення не втрачаються.
8. Переконатися, що `snapshot_json` у `report_versions` не змінився.

## Обмеження

Для цього етапу не додаються нові SQL-міграції: використовуються діючі `report_versions` і `dq_*` (міграція 0013). Технічна розбіжність `d1_migrations` для 0016–0019 потребує окремого аудиту, не запускайте загальний `wrangler d1 migrations apply --remote`.

Збереження до 1200 RAW-рядків не змінюється; передача черги пакетна, неатомарна для всієї версії. Після переривання можливе повторне передавання. Наразі це **ручна перевірка якості довідникових полів**, а не автоматичне виправлення всіх історичних записів чи військова аналітика.
