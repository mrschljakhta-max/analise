# ANALISE — «Чистилище» D1 (перший етап)

## Межі реалізації

Це окремий захищений розділ /api/purgatory, а не публічний прототип.
Додає постійну базу для загальних довідникових значень та ручного
підтвердження, але **не під'єднує парсери Word, Excel і ZIP**.
До появи окремих адаптерів джерел черга не поповнюється зі щоденних файлів.
Тестові входження можна створювати вручну, лише з вигаданими даними.

Модуль не обробляє військові координати, азимути, частоти, цілі,
або зв'язки між оперативними записами. Немає вибору об'єктів за близькістю.

## Реалізовані інтерфейси

- Міграція D1 0013_purgatory.sql: dq_occurrences, dq_rules, dq_audit.
- GET /api/purgatory/data: черга, підсумок, бібліотека правил, журнал.
- GET /api/purgatory/candidates?directory_id=...&q=...: id та name з
  активних записів універсальних directory_entries.
- POST /api/purgatory/ingest: до 80 нейтральних входжень в одному запиті.
- POST /api/purgatory/resolve: режим single — один запис; rule — усі активні входження та майбутні.
- POST /api/purgatory/revoke: відкликання правила.
- POST /api/purgatory/ignore: ігнорування одного входження.
- POST /api/purgatory/retire: деактивація входжень джерела під час його заміни.

Приклад JSON для ingest (тільки після авторизації Access):

~~~json
{
  "items": [
    {
      "directory_id": "example_reference",
      "context_key": "",
      "raw_value": "Синтетичне напісання",
      "source_id": "demo-batch-001",
      "source_ref": "demo-batch-001:row-2:name"
    }
  ]
}
~~~

source_ref — стабільний ідентифікатор поля запису; source_id — версія
джерела; context_key — опційний неоперативний контекст. Не передавати
оперативні дані через тестову форму.

## Ретроспективне правило

Адміністратор обирає конкретний чинний запис довідника.
Правило для (directory_id, context_key, normalized_value) встановлюється
разом із оновленням усіх відповідних **активних** pending або автоматично
вирішених входжень в одній D1 batch-транзакції. Ручні винятки не змінюються.

Оригінальне raw_value зберігається, SQL-тригери записують до/після.
Відкликання правила відновлює статус pending лише для автоматично
вирішених записів; історія залишається.

Ця ретроспекція охоплює тільки входження, зареєстровані в dq_occurrences.
Існуючі таблиці довідників та попередні Word/Excel-звіти не переписуються.
Щоб застосовувати правила до цих джерел, потрібні додаткові адаптери й тести.

## Розгортання після злиття PR у main

1. GitHub Actions → ANALISE D1 schema migration → Run workflow.
2. Перевірити таблиці та тригери dq_.
3. GitHub Actions → Deploy ANALISE API → Run workflow.
4. Відкрити /api/purgatory від імені адміністратора й перевірити
   на вигаданих даних: правило, ретроспекцію, відкликання та аудит.
5. Перевірити, що інші користувачі отримують 403 і на сторінку, і на API.

Модуль не включає завантаження файлів чи змін у чинних довідниках.
