# ANALISE — незалежне RAW-збереження без Чистилища

## Модель обробки

**DOCX/XLSX → автоматичний локальний парсер → RAW у D1 → перевірка довідників у будь-який інший час.**

Перевірка `demo_quality_labels` та локальна ручна перевірка більше **не блокують** RAW-збереження. Дані зберігаються як незмінні знімки. Кожен знімок має `review_status: "pending"` і `checked_against_directories: false`. Не підтверджувати його автоматично.

Цей перший етап має **тільки** роботу з документами **без обмежень доступу**, для яких використання даної інфраструктури погоджене. Ніякого автоматичного збереження при виборі файлу.

## Інфраструктура

Замість нових SQL-таблиць поки використовується наявна таблиця `report_versions` із міграції `0001`:

- `report_name` — namespace `ANALISE-RAW-V1:` + SHA-256 для `user_id + source_name`;
- `version` — номер незмінної версії документа, `status="draft"`;
- `snapshot_json` — повні **розпізнані** RAW-значення, з розділенням Word/Excel, початковими клітинками, групами, номерами рядків, результатом попередньої структурної валідації й зауваженнями;
- `created_by`, `created_at` — наявні поля авторства.

Повторне збереження ідентичного snapshot не створює нової версії. Якщо вміст відрізняється — нова версія без перезапису попередньої.

Обмеження поточного етапу: 12 таблиць, 500 рядків, 190 КіБ JSON snapshot. Нерозпізнані таблиці не можна зберігати як успішно розпізнані. Оригінальні бінарні DOCX/XLSX до D1 **не** потрапляють — тільки результати парсингу.

## Доступ та активація

- Cloudflare Access JWT обов'язковий; лише активна роль `admin`.
- Після отримання окремого погодження використання Cloudflare для конкретного класу документів адміністратор має встановити Worker environment var `RAW_NONRESTRICTED_ENABLED="true"`. Без неї `POST` і `GET` повертають `503` і **не пишуть в D1**. Не активуйте для даних з обмеженим доступом.
- В інтерфейсі потрібна окрема галочка про дозволеність документа та натискання `Зберегти RAW у D1`.
- Ні автоматичного деплою D1-міграцій, ні маніпуляцій із `d1_migrations`: існуючий drift `0016/0019` лишається незмінним.

## Маршрути

- `POST /api/raw-documents` — одна immutable RAW-ревізія;
- `GET /api/raw-documents` — останні 30 ревізій із метаданими;
- `GET /api/raw-documents/:uuid` — перевірка, що RAW-версія читається назад із D1.

Жоден маршрут не виконує порівняння з `dq_occurrences`, не записує нових `dq_rules` і не позначає не перевірені рядки як `verified`.

## Перевірка після релізу

1. За відповідного погодження увімкнути feature flag.
2. Через Cloudflare Access відкрити `/api/generic-preview`.
3. Завантажити цивільний або синтетичний DOCX/XLSX (до 8 МБ), структура має бути автоматично розпізнана.
4. Перед блоком тестового довідника з'явиться `RAW · Зберегти зараз, перевірити пізніше`.
5. Поставити галочку лише для дозволеного документа і натиснути `Зберегти RAW у D1`.
6. Отримати номер версії й статус `pending`, перевірити `Переглянути збережені RAW` і відкриття запису.
7. Без зміни документа повторний клік має повертати ту саму версію. Після редагування/повторного імпорту іншого вмісту з тією самою назвою — нову версію.
8. Після цього можна відкрити блок «Чистилище» **незалежно**; його невідома відповідність не впливає на RAW.

## Наступний етап

Для промислової системи потрібні окремі таблиці індексованих RAW-рядків, прив'язка до правил довідників, рольові дозволи, аудит зміни статусів і плановий механізм публікації `verified`. Це вимагає спочатку безпечного узгодження міграцій та перевірки середовища зберігання.

Тести: `cd api && npm test`.
