# ANALISE — контроль версій синтетичних звітів (v1)

Розділ: `/api/synthetic-upload`. Це безпечний тестовий модуль; реальні
оперативні файли, координати, цілі та частоти не імпортуються.

## Принцип

- **Звітна дата** береться з уже перевіреного синтетичного маніфесту:
  `2026-10-11`. **Дата імпорту** записується окремо сервером.
- Окремий ланцюжок редакцій для кожної пари `(docx|xlsx, report_date)`.
- Перше завантаження документа створює версію `v1`.
- Повторне завантаження того самого синтетичного змісту повторно
  використовує чинну версію й створює лише новий сеанс історії.
- Змінений файл за ту саму дату запускає попередню перевірку й потребує
  явного підтвердження **перед** публікацією нової редакції.
- Попередня редакція залишається незмінною й доступною для перегляду.
- Рішення застосовується тільки до певного виду файла, а не до всього
  ZIP-архіву за раз.
- При одночасному оновленні з іншої вкладки або від іншого оператора
  stale preview відхиляється через порівняння чинної версії в SQL-тригері.
- Архівні сесії до міграції 0016 залишаються доступними в «Історії
  завантажень», але не отримують вигаданий номер версії заднім числом.

## Дані й безпека

Міграція `0016_synthetic_report_versions.sql` додає:
- `demo_report_versions`: незалежні незмінні редаговані **знімки
  результатів** із номером редакції, хешем змісту, датами та автором.
- `demo_report_active`: один чинний ID для кожного виду й звітної дати.
- `demo_report_version_events`: події публікації/повтору й контроль CAS.
- `demo_import_documents.version_id`: посилання з нового сеансу на редакцію
  (для старих документів може бути `NULL`).

Система **не зберігає оригінальні DOCX/XLSX/ZIP**. Рядки в реєстрі
версій — лише ті самі чотири вигадані назви, які дозволені демо-імпортером.
Наявні 48 виправлених входжень та два правила «Чистилища» не видаляються
й не переписуються міграцією. Поточний модуль версій не є повноцінним
механізмом повторної обробки зовнішніх звітних таблиць — він керує
збереженими синтетичними результатами.

## API

- `POST /api/synthetic-upload/inspect?name=...`:
  перевірити файл без запису; повертає `new/same/replacement`,
  чинний `version_id` і номер редакції.
- `POST /api/synthetic-upload/ingest?name=...&session=...`:
  повторно перевіряє вміст, вимагає заголовок
  `x-analise-version-approval` із підтвердженими очікуваними ID,
  застосовує підтверджену заміну.
- `GET /api/synthetic-upload/versions?date=YYYY-MM-DD&kind=docx|xlsx`:
  посторінковий реєстр чинних та архівних редакцій.
- `GET /api/synthetic-upload/versions/{uuid}`: знімок певної редакції.

Усі маршрути admin-only і захищені Cloudflare Access.

## Розгортання

1. Перевірити й об'єднати PR у `main`.
2. GitHub Actions → **ANALISE D1 schema migration** (міграція 0016).
3. GitHub Actions → **Deploy ANALISE API**.
4. Перетягнути старий синтетичний ZIP: очікуємо Word v1, Excel v1.
5. Повторити ідентичний ZIP: досі v1, без дублювання редакцій.
6. Перевірити реєстр і відкрити знімок редакції.
7. Для тесту v2 використовувати лише дозволений змінений синтетичний
   шаблон; система запитає підтвердження.

Робочі довідники ANALISE, чинні записи «Чистилища» і його правила не
повинні змінитися внаслідок міграції.
