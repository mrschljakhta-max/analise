# ANALISE · Історія записів і дій (ретроспективний звіт)

## Результат

Новий захищений розділ `/api/gis-history` з посиланням у нижньому рядку карти `/api/gis-preview`. Працює **лише на читання** з наявною Cloudflare D1 `analise-db`, без міграцій і змін Access.

Відображає:
- історію збереження версій RAW-документів DOCX/XLSX (`report_versions`, тільки `ANALISE-RAW-V1:*`);
- суму рядків збережених версій і структурні записи до перевірки;
- кількість створень/змін у журналі `dq_audit` (Чистилище);
- кількість змін довідників у `directory_entry_audit`;
- кількість змін загальних записів у `record_audit`.

Функції: довільний діапазон до 366 днів, підсумки, діаграма по днях, повна щоденна матриця, експорт агрегатів у CSV для Excel, посилання на існуючі «Збережені документи» і «Чистилище».

## Важливо — це НЕ реконструкція бойових подій

Дати й показники — **час запису документа або аудиту**. Вони не тотожні часові події у Word/Excel. Рядки підсумовуються по версіях; повторне збереження може подвоїти число рядків. Події Чистилища — адміністративні дії з нормалізації, а не виявлення або подавлення БпЛА.

Endpoint повертає **тільки числові підсумки по днях**, без назв документів, особистих даних, унікальних ID, координат, маршрутів, ВП/СП, характеристик станцій, секторів, частот чи військових сирих рядків. Немає жодного SQL-запиту до `operational_report_events`.

## Технічна структура

- `GET /api/gis-history/data?from=YYYY-MM-DD&to=YYYY-MM-DD` — строго адміністративний доступ, дати валідні, 366 днів максимум.
- `GET /api/gis-history`, `/api/gis-history.css`, `/api/gis-history.js` — під чинним Cloudflare Access і перевіркою admin.
- Груповані SQL `SELECT` із параметрами. Жодних SQL-операцій модифікації.
- Відсутність записів відображається як порожній період, SQL-помилки повертають 503, але не вигадані нулі.
- UI не робить запитів до конкретних документів чи військових деталей; лише агреговані числа.

## Що перевірити після публікації

1. Відкрий карту, натисни `Історія та дії ↗`, або відкрий `/api/gis-history`.
2. Встанови період, коли точно були завантаження документів, і натисни `Показати історію`.
3. Перевір кількість RAW-версій, щоденні значення, рядки у версіях, дії Чистилища.
4. Експортуй CSV для Excel.
5. За потреби відкрий окремо `Збережені документи` для перегляду первинних рядків або `Чистилище` для історії рішень.
6. Якщо нічого немає, перевір дати **завантажень**, а не дати подій у первинному файлі. У цьому етапі немає карти історичних військових точок.

Серверні тести: `cd api && npm test`. Без змін production D1 schema або Cloudflare Access.

## Уточнення від 18.10.2026: діагностика історії

Раніше один графік зі спільним максимумом порівнював RAW-версії та адміністративні аудит-записи. Це приховувало малі стовпчики версій, коли записів у Чистилищі було значно більше. Виправлено: **три графіки з незалежними шкалами** — RAW-версії, рядки по версіях і аудиторські записи; над кожним стовпчиком точне число.

Окремо додано **кількість унікальних документів у вибраному періоді**, що рахується `COUNT(DISTINCT report_name)` і не підсумовується по днях. Збережені версії того самого документа можуть бути декілька разів у різні дні.

Журнал Чистилища уточнено за `entity_type`: створення/редагування **значень (occurrence)** окремо від створення/редагування **правил (rule)**. Колишні великі числа `quality_created` або `quality_updated` сумували обидва типи й не означали кількість підтверджених або перевірених значень.

Таблиця містить розкладені лічильники та явний перелік чотирьох джерел D1. Нових записів у базу не внесено; не торкаємося історичних операційних звітів або їхніх просторових даних.
