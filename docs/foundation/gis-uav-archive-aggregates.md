# ANALISE · Історичні дані БпЛА з Cloudflare D1

## Визначення джерела

Цей етап читає **справжні структуровані записи** у `operational_report_events`, пов'язані з `operational_report_sessions`. Беруться тільки `source_type='pbd_word'` та завершені сесії зі статусом `committed`. Факт збереження RAW у `report_versions` **не гарантує наявності** таких подій у структурованій таблиці.

Ретроспективна сторінка доступна за адресою `/api/gis-uav-archive` через Cloudflare Access тільки активному адміністратору. Посилання додано на сторінку карти `/api/gis-preview` і в адміністративну історію `/api/gis-history`.

## Доступні функції

- Вибір **календарного року** та категорії: FPV, крило, мультироторні, невизначений клас.
- Квартальні діаграми й таблиця **лише** за завершеними та достатньо давніми періодами.
- CSV експорт тільки вже розкритих агрегованих категорій, придатний для відкриття Excel.
- Явне джерело даних і пояснення ситуації, коли дані відсутні чи D1 не має відповідної структури.

## Захист деталізації

- **Не менше 90 днів затримки** від поточного моменту й **тільки повністю завершені квартали**.
- Для кварталу і класу БпЛА чисельне значення видно лише при **20 і більше** записах. Менші клітинки API повертає як `null`, а інтерфейс показує «—».
- Немає географічного розподілу, адрес, населених пунктів, координат, маршрутів, полігонів, радіусів і секторів станцій.
- API не повертає військових об'єктів, підрозділів, назв станцій, частот, тексту первинних звітів або окремих подій.
- Сервер не дозволяє деталізацію за місяцем, днем, місцевістю, підрозділом чи точним типом техніки. Дозволено тільки параметр `year`.
- `GET /api/gis-uav-archive/data?year=2025` — виключно агреговані `SELECT` з параметризацією; жодних міграцій, змін Cloudflare Access або запису в D1.

**Не слід використовувати цю сторінку для відтворення операційної обстановки.** Історичне значення документів саме собою не є підставою для географічної деталізації подій.

## Обробка нестачі даних

Якщо структурованих записів за допустимий рік немає, усі клітинки будуть «—»; це **не** підтвердження відсутності реальних подій. Якщо таблиці або міграції відсутні, API відповідає **503**, а інтерфейс покаже діагностику недоступного джерела, не вигадуючи цифри. Наявні RAW-документи залишаються в окремому архіві. **Немає автоматичного переносу RAW-документів у події:** це окрема процедура із валідацією.

## Тестування

1. Відкрити `/api/gis-uav-archive` після Cloudflare Access.
2. Обрати дозволений минулий рік і натиснути «Читати D1».
3. Переконатися, що відображено тільки завершені квартали, а не індивідуальні події.
4. Перевірити категорійний фільтр і CSV експорт; подавлені категорії в CSV порожні.
5. Порівняти джерело з журналом збережень RAW на `/api/gis-history` та за потреби відкрити `/api/saved-documents`.
6. Автоматичні тести: `cd api && npm test`. Без змін схеми D1.

## Відоме обмеження

Проста нормалізація назв БпЛА за ключовими словами (наприклад, FPV/фпв, крило, мульти-/квадро-) може віднести невідомі назви до «Без визначеного класу». Для точнішої класифікації потрібна окрема контрольована схема довідників, але вона не повинна розкривати оперативні деталі.

## 18.10.2026 — діагностика реального сховища

Після запуску на сторінці з'явилося `Структурований архів подій недоступний або міграція 0018 не застосована`. Ця стара помилка була надто широкою: `catch` позначав **будь-який** SQL-збій як можливу відсутність міграції, не перевіряючи фактичні таблиці.

Нова реалізація перед читанням структурованих подій виконує **лише read-only** перевірку наявності таблиць через `sqlite_master`:

- Якщо `operational_report_events` чи `operational_report_sessions` відсутні, повертається `200`, `source_status=schema_missing` і порожні структуровані агрегати. Це означає **не «нуль подій»**, а відсутнє структуроване джерело.
- Незалежно читається кількість версій `ANALISE-RAW-V1:*` із `report_versions` **за роком збереження**, разом зі збереженою кількістю рядків. Це метадані збереження, не вміст або хронологія фактичних подій. Значення RAW не підставляються в розподіл типів БпЛА.
- Якщо обидві структуровані таблиці наявні, але сам агрегатний SQL не виконується, повертається `503`, `source_status=structured_query_failed`, і доступна окремо метаінформація RAW. Причина може бути несумісністю схеми або іншим SQL-збоєм; система **не вигадує**, яка саме міграція відсутня.
- Якщо не вдається навіть прочитати список таблиць, повертається `503`, `source_status=database_unavailable`, без внутрішніх SQL-помилок чи секретів.
- Якщо структурований запит успішний, повертається `source_status=structured_available`; попередні обмеження архівності, квартальної деталізації та порога відображення залишаються.

**Жодні міграції автоматично не запускати.** Існуючий `migrate-d1.yml` застосовує всі очікувані міграції в production і не повинен запускатися до перевірки реєстру міграцій, схеми та резервного відновлення. Окреме завантаження/перетворення військових RAW-звітів у структуровані оперативні події також не входить до цього виправлення.

## Аудит структури D1 (наступний етап, без міграцій)

Після перевірки наявності таблиць Worker виконує додаткові read-only запити:

- `SELECT name FROM pragma_table_info(?)` — перевірка **лише** обов'язкових для агрегатного API колонок, без читання вмісту подій;
- `SELECT COUNT(*) AS applied FROM d1_migrations WHERE name=?` — незалежна ознака, чи зареєстрована міграція `0018_operational_reports.sql` у журналі (якщо журнал існує).

Стани API тепер розрізняють `schema_missing`, `schema_incompatible`, `schema_check_failed`, `structured_query_failed`, `database_unavailable` та `structured_available`. Статус RAW, як і раніше, діагностується незалежно, а для неузгоджених колонок RAW використовується `schema_incompatible`.

Поле `schema_diagnostics` повертає лише відсутні **назви очікуваних колонок** та загальний стан реєстрації міграції. Значення рядків, назви БпЛА, координати й документи не повертаються.

Розбіжність між журналом міграцій і фактичною схемою — **сигнал для аудиту**, не підстава запускати міграції автоматично. Щоб довести production-стан, окремо перевірити після Cloudflare Access відповідь `/api/gis-uav-archive/data?year=2026` та ідентичність розгорнутої версії Worker; проходження CI і GitHub Pages само по собі не підтверджує Worker Deploy.

## Ручний production-аудит D1 без міграцій

У PR з перевіркою схеми додано workflow `.github/workflows/audit-d1-readonly.yml` — **ANALISE D1 read-only schema audit**.

Після об'єднання PR він доступний у GitHub Actions через **Run workflow** для `main`. Він запускає через наявні GitHub Secrets рівно два запити **SELECT** до production `analise-db`:

1. Перелік лише `report_versions`, `operational_report_sessions`, `operational_report_events`, `d1_migrations`, які фактично існують.
2. Перелік лише тих колонок цих RAW/structured таблиць, які використовує поточний API.

Він не використовує `migrate-d1.yml`, не застосовує жодної міграції, не підміняє імпорт, не читає вміст звітів та не змінює стан D1.

Окремо після об'єднання PR і **ручного** `Deploy ANALISE API` сторінка `/api/gis-uav-archive` показуватиме точні назви відсутніх таблиць (поле `schema_diagnostics.missing_tables`), нестачу колонок, стан журналу 0018 і метадані RAW. Деплой і аудит — різні дії; GitHub Pages не публікує Worker.

Якщо структурованих таблиць немає, їхня схема має бути узгоджена **до** окремо підтвердженої міграції; імпорт RAW у структуровані події не відбувається автоматично. Не запускати загальний `migrate-d1.yml` на підставі одного скриншота.
