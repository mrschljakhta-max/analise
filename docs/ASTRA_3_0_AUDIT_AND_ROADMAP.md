# ANALISE → ASTRA 3.0: аудит і план поетапного розвитку

**Дата:** 15.10.2026  
**База:** чинний репозиторій `mrschljakhta-max/analise`, гілка `main` станом на аудит.  
**Правило:** розвивати наявний сайт, не створювати паралельну платформу й не переносити до публічного середовища службові дані.

## 2. Погоджена предметна поведінка (пріоритет над ТЗ 0.1/0.2)

- Excel і Word: два незалежні журнали та дві незалежні аналітичні панелі.
- Один рядок = один самостійний запис; однакові рядки можуть бути різними подіями.
- Один документ кожного типу на звітну добу; звітну дату оператор вводить вручну як дату завершення періоду.
- 15:00 (ПБД) і 18:00 (ОЧ СЕВ) — орієнтири, не жорсткі умови валідації.
- Виправлений документ створює **нову версію всього добового набору**, не автоматичне зіставлення кожного рядка.
- Актуальною є лише одна версія для типу й звітної дати; попередні версії залишаються в архіві.
- Невідомі значення не блокують активацію версії: вони потрапляють до «Чистилища».
- Порожні значення дозволені; у статистиці «Не зазначено» та «Очікує перевірки» — різні категорії.
- Перевірка окремих полів незалежна; в аналітиці використовуються лише підтверджені для відповідного розрахунку значення.
- Підтверджені довідникові аліаси застосовуються повторно; при архівуванні основного запису аліаси деактивуються.
- Нормалізація регістру, пробілів, апострофів і дефісів допустима без зміни RAW; підозрілі літери іншого алфавіту й цифри лише підсвічуються для рішення оператора.
- Фільтри аналітичної панелі спільні, підтримують множинний вибір, але після виходу не зберігаються.

## 3. Реалізовано в першому оновленні цієї гілки

1. Окремий модуль `report-versions.js` із перевіркою ручної звітної дати й розрахунком версії.
2. У структурному перегляді XLSX/DOCX дата починається порожньою і є обов'язковою для реєстрації.
3. Для того самого типу документа й тієї самої звітної дати новий файл створює наступну версію; попередня стає неактуальною.
4. Ідентичний за байтами документ удруге не реєструється, навіть після заміни його новою версією.
5. В історії імпорту показано дату, номер версії та статус («Актуальна версія» / «Попередня версія»).
6. Форматні зауваження не блокують реєстрацію версії; фіксується їхня кількість.
7. Автоматизовані Node-тести й GitHub Actions перевіряють цей окремий механізм.

**Важлива межа:** поки що це **облік версій у пам'яті відкритої вкладки**, а не серверний архів. Повноцінного «Чистилища», перенесення рядків у предметні журнали та RAW/STAGING/VERIFIED у цьому оновленні ще немає.

## 5. Безпека й відкриті рішення

GitHub Pages і публічний GitHub-репозиторій не є погодженим сховищем службових документів. Поточний клієнтський парсер не завантажує дані на сервер, але це **не** замінює рішення щодо режиму захисту, авторизації, контролю браузера, журналу доступу чи дозволеності обробки конкретних категорій даних.

До роботи з реальними документами окремо затвердити інфраструктуру, правила доступу та резервування. До того часу тестувати **лише синтетичні або належно знеособлені дані**.

## 6. Примітка щодо старих механізмів

Старий навчальний облік «джерело+код» та зразковий звіт 15:00–15:00 залишаються в демочастині до окремого рефакторингу. Вони **не описують** погоджену предметну модель Excel/Word і не можуть непомітно ставати алгоритмом імпорту ASTRA 3.0.
